# แผนงาน: จัดการลบหรือระงับกิจกรรมที่เผยแพร่แล้ว (Delete Activity)

อ้างอิงข้อกำหนด: [spec.md](./spec.md) (Draft v2)

## 1. สรุปแนวทาง

1. Admin สามารถเลือกกิจกรรมที่เผยแพร่แล้วและเลือกการกระทำเป็น “ลบ” หรือ “ระงับ” ได้ โดยต้องผ่านการตรวจสอบสิทธิ์ก่อนดำเนินการ (FR-DEL-01, FR-DEL-02, ACC-ADMIN-01)

2. ก่อนยืนยันการลบหรือระงับ Admin ต้องระบุเหตุผล และระบบต้องปฏิเสธการดำเนินการหากไม่มีเหตุผลตามข้อกำหนด (FR-DEL-03, IF-REASON-01)

3. การลบและการระงับใช้แนวทาง soft delete / hidden state เดียวกัน โดยไม่ลบข้อมูลกิจกรรมออกจากฐานข้อมูล เพื่อให้ Admin ยังสามารถตรวจสอบข้อมูลย้อนหลังได้ (FR-DEL-04, FR-DEL-05, ASM-02, ASM-04)

4. กิจกรรมที่ถูกลบหรือระงับต้องไม่ปรากฏในรายการกิจกรรมที่นักศึกษาสามารถมองเห็น แต่ข้อมูลกิจกรรมยังคงถูกจัดเก็บไว้ในระบบ (IF-HIDE-01, FR-DEL-05)

5. ทุกการลบหรือระงับต้องสร้าง Audit Log เพื่อบันทึกผู้ดำเนินการ เวลา เหตุผล และประเภทการดำเนินการ เพื่อรองรับการตรวจสอบย้อนหลัง (FR-DEL-06, NFR-DEL-03, ACC-AUDIT-01)

6. การตรวจสอบสิทธิ์ต้องเกิดทั้งก่อนเปิดฟอร์มการดำเนินการและอีกครั้งเมื่อ Admin กดยืนยัน เพื่อป้องกันการดำเนินการโดยผู้ไม่มีสิทธิ์ (IF-ADMIN-01, ACC-ADMIN-01)

## 3. โมเดลข้อมูล

| Entity           | ฟิลด์หลัก                                                              | รองรับ                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Activity         | `id`, `status`, `visibility` หรือฟิลด์สถานะที่มีอยู่                   | ใช้ระบุสถานะเผยแพร่และสถานะที่ถูกลบ/ระงับ โดยยังเก็บข้อมูลกิจกรรมไว้ (FR-DEL-01, FR-DEL-05, IF-HIDE-01)                |
| ActivityAuditLog | `id`, `activity_id`, `admin_id`, `action_type`, `reason`, `created_at` | เก็บผู้ดำเนินการ ประเภทการดำเนินการ เหตุผล และเวลา เพื่อรองรับการตรวจสอบย้อนหลัง (FR-DEL-06, NFR-DEL-03, ACC-AUDIT-01) |

การออกแบบควรใช้ฟิลด์สถานะหรือ visibility ที่มีอยู่แล้วของกิจกรรมหากระบบมีอยู่ โดยไม่สร้างข้อมูลซ้ำโดยไม่จำเป็น

การลบหรือระงับไม่ควรลบ record ของกิจกรรมออกจากฐานข้อมูล เพราะข้อมูลยังต้องสามารถตรวจสอบย้อนหลังโดย Admin ได้

## 4. API / หน้าจอ

* `GET /admin/activities` — อ่านรายการกิจกรรมที่ Admin มีสิทธิ์จัดการ โดยเน้นกิจกรรมที่อยู่ในสถานะเผยแพร่แล้ว (FR-DEL-01, FR-DEL-02)

* `POST /admin/activities/{activity_id}/delete` — ตรวจสอบสิทธิ์ ตรวจสอบสถานะกิจกรรม ตรวจสอบเหตุผล แล้วเปลี่ยนกิจกรรมเป็น hidden/soft deleted พร้อมบันทึก Audit Log (FR-DEL-03, FR-DEL-05, FR-DEL-06)

* `POST /admin/activities/{activity_id}/suspend` — ตรวจสอบสิทธิ์ ตรวจสอบสถานะกิจกรรม ตรวจสอบเหตุผล แล้วเปลี่ยนกิจกรรมเป็น hidden/soft deleted พร้อมบันทึก Audit Log (FR-DEL-03, FR-DEL-05, FR-DEL-06)

* `GET /admin/activities/{activity_id}/audit-logs` — อ่าน Audit Log ของกิจกรรมสำหรับ Admin เพื่อรองรับการตรวจสอบย้อนหลัง (FR-DEL-06, NFR-DEL-03)

* `หน้า Admin รายการกิจกรรม` — แสดงกิจกรรมที่เผยแพร่แล้วและเปิดทางให้ Admin เลือกการกระทำที่มีสิทธิ์ดำเนินการ (FR-DEL-01, FR-DEL-02)

* `หน้าต่างยืนยันการลบ/ระงับ` — ให้ Admin ระบุเหตุผลก่อนยืนยัน และปฏิเสธการยืนยันหากไม่มีเหตุผล (FR-DEL-03, IF-REASON-01)

* `รายการกิจกรรมฝั่งนักศึกษา` — ไม่แสดงกิจกรรมที่ถูกลบหรือระงับแล้ว (FR-DEL-05, IF-HIDE-01)

ชื่อ path ของ API ข้างต้นเป็นข้อเสนอเชิงออกแบบ ไม่ใช่ข้อกำหนด API โดยตรงจาก spec

## 7. ลำดับงาน

1. ตรวจสอบ flow แบบ end-to-end ตั้งแต่ Admin เลือกกิจกรรม เลือกการกระทำ ระบุเหตุผล และยืนยัน ให้ตรงกับ FR-DEL-01 ถึง FR-DEL-07

2. เชื่อมการอนุญาตเข้าถึงหน้าและ API เข้ากับการตรวจสอบสิทธิ์ Admin และปฏิเสธผู้ใช้ที่ไม่มีสิทธิ์ (IF-ADMIN-01, ACC-ADMIN-01)

3. เพิ่มการตรวจสอบว่ากิจกรรมต้องอยู่ในสถานะเผยแพร่ก่อนจึงสามารถลบหรือระงับได้ (FR-DEL-01, FR-DEL-02)

4. สร้างฟอร์ม/หน้าต่างยืนยันการลบหรือระงับ โดยบังคับให้ Admin ระบุเหตุผลก่อนดำเนินการ (FR-DEL-03, IF-REASON-01)

5. เพิ่มการเปลี่ยนสถานะกิจกรรมเป็น hidden/soft deleted โดยไม่ลบข้อมูลกิจกรรมออกจากระบบ (FR-DEL-05, IF-HIDE-01, ASM-02, ASM-04)

6. ปรับการแสดงรายการกิจกรรมฝั่งนักศึกษาให้ไม่แสดงกิจกรรมที่ถูกลบหรือระงับแล้ว (FR-DEL-05, IF-HIDE-01)

7. เพิ่มการบันทึก Audit Log หลังการดำเนินการสำเร็จ โดยบันทึกผู้ทำ เวลา เหตุผล และประเภทการดำเนินการ (FR-DEL-06, NFR-DEL-03, ACC-AUDIT-01)

8. ตรวจสอบกรณีที่ผู้ใช้ไม่มีสิทธิ์หรือ session เปลี่ยนแปลงระหว่างเปิดฟอร์มกับการยืนยัน เพื่อให้ระบบตรวจสิทธิ์ซ้ำก่อนดำเนินการจริง (IF-ADMIN-01, ACC-ADMIN-01)

9. รันทดสอบตาม Acceptance Criteria ที่เกี่ยวข้อง และตรวจย้อนกลับกับ Traceability ระหว่าง Requirement, Constraint และ Acceptance Criteria ใน `spec.md`

## 8. สิ่งที่ยังไม่ทำ

* ไม่ลบข้อมูลกิจกรรมออกจากฐานข้อมูลแบบ hard delete เนื่องจากต้องเก็บข้อมูลไว้สำหรับ Admin ตรวจสอบย้อนหลัง

* ไม่สร้างความแตกต่างเชิงธุรกิจระหว่าง “ลบ” และ “ระงับ” หาก spec ปัจจุบันยืนยันให้ใช้ soft delete/hidden state แบบเดียวกัน

* ไม่อนุญาตให้ผู้ใช้ที่ไม่ใช่ Admin ดำเนินการลบหรือระงับกิจกรรม

* ไม่อนุญาตให้ลบหรือระงับกิจกรรมที่ไม่ได้อยู่ในสถานะเผยแพร่

* ไม่เปลี่ยนแปลงข้อมูลกิจกรรมส่วนอื่นที่ไม่เกี่ยวข้องกับการซ่อน/เปลี่ยนสถานะ

* ไม่ลบ Audit Log หลังจากบันทึกแล้ว เพื่อให้สามารถตรวจสอบย้อนหลังได้
