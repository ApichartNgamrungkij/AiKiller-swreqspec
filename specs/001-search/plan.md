# แผนงานฟีเจอร์: ค้นหาและดูกิจกรรม (Search)

## 1. สรุปแนวทาง
ฟีเจอร์นี้จะสร้างหน้า Search & Detail ที่อนุญาตให้นักศึกษาค้นหาและกรองกิจกรรมตามประเภทและช่วงเวลาว่างที่กรอกไว้เอง โดยคำนึงถึงสถานะกิจกรรมและการชนกับตารางส่วนตัวของนักศึกษา เพื่อให้ผู้ใช้เห็นข้อมูลก่อนตัดสินใจลงทะเบียนผ่าน Google Form ต่อไป

ฟีเจอร์นี้รองรับบทบาทนักศึกษาเป็นหลัก และมีการแสดงข้อมูลตามบทบาทผู้ดูแลกิจกรรมและ Admin ตามที่ระบุใน spec แต่ไม่ได้ทำกระบวนการลงทะเบียนจริงหรือจัดการกิจกรรมภายในฟีเจอร์นี้

แนวทางการสร้างจะเริ่มจากการแสดงรายการกิจกรรมพร้อมสถานะและรูปแบบคอนฟิกตัวกรองก่อน จากนั้นจะเพิ่มรายละเอียดกิจกรรมและการแจ้งเตือนเมื่อมีความชนกับตารางส่วนตัว ก่อนจบด้วยการปรับประสิทธิภาพและความเข้ากันได้ของหน้าจอ

ทุกชิ้นส่วนของ plan นี้จะเชื่อมกลับไปยัง FR-SRCH-01 ถึง FR-SRCH-05 และ AC-SRCH-01 ถึง AC-SRCH-08 ตาม spec ที่รับรองแล้ว

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React + Vite สำหรับหน้าเว็บผู้ใช้ | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สำหรับ UI ของ Search List และ Detail View ตาม FR-SRCH-01 ถึง FR-SRCH-05 |
| Python FastAPI สำหรับ API | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สำหรับโหลดกิจกรรมและประมวลผลกรอง/เชื่อมตารางส่วนตัว |
| Google Sheets API แบบ polling | IF — ข้อมูลจำนวนผู้ลงทะเบียนดึงมาจาก Google Sheets ผ่าน API แบบ poll เป็นระยะ (ทุก 1–2 นาที) จึงมีความหน่วงได้เล็กน้อย | ใช้เพื่อรับสถานะผู้ลงทะเบียนและอัปเดตสถานะกิจกรรมตาม IF ระบบต้องอัปเดตภายใน 1 นาทีหลังข้อมูลอัปเดต |
| HTTPS | NFR — ระบบต้องส่งข้อมูลระหว่างผู้ใช้กับเซิร์ฟเวอร์ผ่านการเข้ารหัส (HTTPS) เพื่อปกป้องข้อมูลส่วนตัวของนักศึกษา | ใช้ในสภาพแวดล้อม deployment และ frontend-backend communication |
| Browser-side filtering และ server-side filtering แบบผสม | FR-SRCH-02, FR-SRCH-03, IF — ต้องรองรับผู้ใช้งานพร้อมกันได้ ~5,000 คน | ใช้คัดกรองประเภทและช่วงเวลาว่างให้เร็วและมีประสิทธิภาพ |
| การแสดงสีแดงและข้อความเตือนบนกิจกรรมที่ชนกับตาราง | IF — เมื่อพบว่าตารางชนกัน ระบบต้องแสดงกิจกรรมไว้พร้อมคำเตือนสีแดงทั้งกิจกรรมและตารางเรียนที่ชน | จัดทำเป็น UI state และ status badge บนรายการผลลัพธ์ |

## 3. โมเดลข้อมูล

### 3.1 Activity
| ฟิลด์หลัก | คำอธิบาย | รองรับ FR |
|---|---|---|
| id | รหัสกิจกรรม | FR-SRCH-01, FR-SRCH-03, FR-SRCH-05 |
| title | ชื่อกิจกรรม | FR-SRCH-01, FR-SRCH-05 |
| category | ประเภทกิจกรรม (5 ประเภทที่มหาวิทยาลัยรับรอง) | FR-SRCH-02, FR-SRCH-03 |
| status | สถานะกิจกรรม เช่น เปิดรับ / เต็มแล้ว | FR-SRCH-01, FR-SRCH-03 |
| startAt, endAt | วันและเวลาปฏิบัติกิจกรรม | FR-SRCH-02, FR-SRCH-05 |
| hoursAwarded | ชั่วโมงจิตอาสาที่ได้รับ | FR-SRCH-05 |
| location | สถานที่ | FR-SRCH-05 |
| availableSlots, bookedSlots | จำนวนที่รับและจำนวนที่ลงทะเบียนแล้ว | FR-SRCH-01, FR-SRCH-03 |
| googleFormUrl | ลิงก์ไปยัง Google Form สำหรับลงทะเบียนต่อ | FR-SRCH-05 |
| approvalStatus | สถานะอนุมัติสำหรับ Admin ดู | เป็นระบบกลาง/บทบาท Admin |
| isDeleted | สถานะลบสำหรับประวัติของ Admin | เป็นระบบกลาง/บทบาท Admin |

### 3.2 StudentSchedule
| ฟิลด์หลัก | คำอธิบาย | รองรับ FR |
|---|---|---|
| studentId | รหัสนักศึกษาในระบบ (ไม่ใช่เลขบัตรประชาชน) | FR-SRCH-02, FR-SRCH-03 |
| availabilitySlots | ตารางเวลาว่างที่นักศึกษากรอกไว้เอง | FR-SRCH-02, FR-SRCH-03 |
| lastUpdatedAt | วันเวลาล่าสุดที่นักศึกษาอัปเดตตาราง | FR-SRCH-02 |

### 3.3 CollisionWarning
| ฟิลด์หลัก | คำอธิบาย | รองรับ FR |
|---|---|---|
| activityId | กิจกรรมที่ชน | FR-SRCH-02, FR-SRCH-03 |
| studentScheduleId | ตารางนักศึกษาที่ชน | FR-SRCH-02, FR-SRCH-03 |
| overlapStart, overlapEnd | ช่วงเวลาที่ชนกัน | FR-SRCH-02, FR-SRCH-03 |
| severity | ระดับสีแดง/คำเตือน | IF — เมื่อพบว่าตารางชนกัน |

หมายเหตุ: โมเดลนี้ต้องไม่มีการเก็บข้อมูลส่วนตัวเกินสิ่งที่จำเป็นตาม spec และไม่เก็บข้อมูลที่ spec ไม่ระบุ เช่น เลขบัตรประชาชน หรือข้อมูลตารางเรียนจากมหาวิทยาลัยโดยตรง

## 4. API / หน้าจอ

### 4.1 หน้าจอ
- หน้า Search list: รองรับ FR-SRCH-01, FR-SRCH-02, FR-SRCH-03, FR-SRCH-04
- หน้า Detail activity: รองรับ FR-SRCH-05
- หน้าจอสำหรับผู้ดูแล / Admin: รองรับบทบาทตาม Scope แต่ไม่ใช่ฟีเจอร์การลงทะเบียน

### 4.2 API
- GET /api/activities: คืนกิจกรรมตามบทบาทผู้ใช้ พร้อมสถานะเต็ม/ว่างและประเภทที่แสดงได้; รองรับ FR-SRCH-01, FR-SRCH-03
- GET /api/activities?category=...&timeWindow=...: รองรับการกรองประเภทและช่วงเวลาว่าง; รองรับ FR-SRCH-02, FR-SRCH-03
- GET /api/activities/:id: คืนรายละเอียดกิจกรรมพร้อมข้อมูลที่แสดงก่อนลงทะเบียน; รองรับ FR-SRCH-05
- GET /api/student-schedules/me: คืนช่วงเวลาว่างที่นักศึกษาได้กรอกไว้เอง; รองรับ FR-SRCH-02
- GET /api/activities/:id/collision-status: คืนสถานะชนกับตารางส่วนตัว พร้อม warning; รองรับ IF — เมื่อพบว่าตารางชนกัน

Input/Output หลัก:
- Request params: category, date, timeWindow, role
- Response: list of activities, warnings, detail payload, status badge

## 5. ตารางตรวจ Constraints

| Constraint ID / ข้อความใน spec | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| IF — ห้ามดึงข้อมูลจากระบบตารางเรียนของมหาวิทยาลัยโดยตรง — ต้องใช้เฉพาะข้อมูลตารางที่นักศึกษากรอกเองในระบบเท่านั้น | StudentSchedule และ API /api/student-schedules/me | ใช้แล้ว |
| IF — ห้ามรับประกันว่าสถานะ "เต็ม/ว่าง" เป็น real-time แบบเป๊ะ — ข้อมูลจำนวนผู้ลงทะเบียนดึงมาจาก Google Sheets ผ่าน API แบบ poll เป็นระยะ (ทุก 1–2 นาที) จึงมีความหน่วงได้เล็กน้อย | Google Sheets API polling; status badge refresh logic | ใช้แล้ว |
| IF — ระบบต้องอัปเดตสถานะ "เต็มแล้ว/ยังรับสมัคร" ภายใน 1 นาทีหลังข้อมูลใน Google Sheets อัปเดต และต้องไม่ช้ากว่า 2 นาที | polling interval + refresh strategy ใน Activity status sync | ใช้แล้ว |
| DOM — ห้ามแสดงกิจกรรมที่ไม่ใช่ 1 ใน 5 ประเภทที่มหาวิทยาลัยรับรอง | category filter validation และ datasource filter | ใช้แล้ว |
| IF — เมื่อพบว่าตารางชนกัน ระบบต้องแสดงกิจกรรมไว้พร้อมคำเตือนสีแดงทั้งกิจกรรมและตารางเรียนที่ชน โดยไม่ block การดูรายละเอียด และห้ามตัดสินใจแทนนักศึกษา | CollisionWarning, UI badge, detail page accessibility | ใช้แล้ว |
| IF — ต้องรองรับผู้ใช้งานพร้อมกันได้ในระดับ ~5,000 คน/ภาคการศึกษา — การค้นหา/กรองต้องไม่ทำให้ระบบช้าลงเมื่อมีคนเข้าดูพร้อมกันจำนวนมาก และต้องตอบสนองต่อคำขอภายใน 2 วินาที | server-side filter, caching, pagination strategy, response time benchmark | ใช้แล้ว |
| NFR — ระบบต้องส่งข้อมูลระหว่างผู้ใช้กับเซิร์ฟเวอร์ผ่านการเข้ารหัส (HTTPS) | deployment security guideline | ใช้แล้ว |
| NFR — กระบวนการเตรียมข้อมูลให้พร้อมส่งเข้า REG ต้องทำได้ภายใน 1 วันทำการเมื่อเอกสารครบถ้วน | ยังไม่ใช้ใน plan เนื่องจากไม่ใช่ฟีเจอร์ Search โดยตรงและไม่ปรากฏในรายละเอียดการทำงานของ UI/API นี้ | ยังไม่ได้ใช้ เพราะเป็น system-wide NFR ที่ต้องมีคนจัดการในระดับระบบกลาง |
| NFR — ระบบต้องมี Audit Log บันทึกการอนุมัติ/ปฏิเสธเอกสารของ Admin เพื่อตรวจสอบย้อนหลังได้ | ยังไม่ใช้ใน plan เนื่องจากไม่ตรงกับหน้าดูกิจกรรมหรือฟีเจอร์ Search โดยตรง | ยังไม่ได้ใช้ เพราะเป็น system-wide NFR และไม่ใช่ functional scope ของ Search |

## 7. ลำดับงาน

1. ตั้งโครงสร้าง UI ของ Search list และ Detail view ตาม FR-SRCH-01, FR-SRCH-05 และ AC-SRCH-01, AC-SRCH-04
2. เชื่อมข้อมูลกิจกรรมจาก API เพื่อแสดงรายการที่มีสถานะเต็ม/ว่างตาม FR-SRCH-01 และ AC-SRCH-01
3. Implement ตัวกรองประเภทและช่วงเวลาว่างตาม FR-SRCH-02 และ AC-SRCH-02, AC-SRCH-03
4. Implement การแสดงผลลัพธ์กรองและข้อความไม่พบตาม FR-SRCH-03, FR-SRCH-04 และ AC-SRCH-05
5. Implement รายละเอียดกิจกรรมพร้อมลิงก์ Google Form และข้อมูลแสดงก่อนลงทะเบียนตาม FR-SRCH-05 และ AC-SRCH-04
6. Implement collision warning สีแดงและการแสดงตารางที่ชนตาม IF และ AC-SRCH-03
7. Implement polling status sync กับ Google Sheets และการอัปเดตสถานะกิจกรรมตาม IF และ AC-SRCH-07
8. Validate performance และ responsive layout สำหรับ 5,000 คน/กรณีมือถือ/ไอแพด ตาม IF, NFR, AC-SRCH-08
9. ทำการทดสอบครบทุก AC และตรวจทานความสอดคล้องกับ Scope/Out of Scope

## 8. สิ่งที่ยังไม่ทำ

ไม่มี Open Question ที่ค้างใน spec ปัจจุบัน หลังจากทีมยืนยันคำตอบแล้ว แต่ยังมีข้อที่ต้องระวังให้ติดตามต่อไปดังนี้:

- Q-01: ข้อความ Requirement ที่เกี่ยวข้องในเอกสารต้นทางเคยถูกยืนยันว่าครบถ้วนแล้ว จึงไม่ได้มีกำหนดเพิ่มเติมในแผนนี้
- Q-02: เป็นฟีเจอร์ของตัวระบบเอง ไม่ได้เจาะจงตัวอื่นตัวเดียว จึงไม่ต้องมีงานแยกนอก Search
- Q-03: เป็น system-wide NFR ซึ่งยังไม่ได้ implement ในฟีเจอร์ Search โดยตรง แต่ Search จะต้องอยู่ภายใต้ข้อกำหนด REG / Audit Log ที่ระบบกลางกำหนด

สรุปคือ plan นี้ยังไม่สร้างสิ่งใดที่อยู่นอก scope ของ Search และยังไม่ได้ตัดสินใจแทนทีมในเรื่องที่ spec ยังไม่ได้กำหนดชัด จนกว่าจะมีคำตอบเพิ่มเติมจากทีม
